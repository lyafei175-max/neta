## 一、TBOE 帧格式

**对应文件**：`NetaL/BLE/TboeFrameCodec.swift` → `FrameLayout`

| 项 | 字段 | 当前占位值 | 怎么定 |
|---|---|---|---|
| 帧头魔数 | `magic` | `[0xAA, 0xAA]` | 跑分析脚本，看「常见协议头前缀检验」输出 |
| 跳过的固定字段 | `magicSkip` | `0` | 若魔数后有版本号/保留位，填字节数 |
| 长度字段偏移 | `lengthOffset` | `2` | 脚本提示的「取值少」位置 |
| 长度字段宽度 | `lengthBytes` | `1` | 观察长帧长度最大能到多少（>255 则为 2 字节） |
| 长度含自身 | `lengthIncludesHeader` | `true` | 比对声明值与实际长度 |
| 序号偏移 | `sequenceOffset` | `nil` | 同指令连发两次，找差异位 |
| 类型偏移 | `typeOffset` | `3` | 对照帧类型分布 |
| 类型宽度 | `typeBytes` | `1` | 同上 |
| 校验算法 | `checksum` | `.xor` | 脚本「校验和假设检验」会给出结论 |
| 校验码宽度 | `checksumBytes` | `1` | 若显示「CRC16」则填 2 |

### 分析脚本能给出的答案

```
字段结构推断
  字节[ 0] 全部帧恒定 = 0xAA   ← 魔数
  字节[ 1] 全部帧恒定 = 0xAA
  字节[ 2] 全部帧恒定 = 0x00   ← 跳过的字段
  字节[ 3] 取值少: 0x06(2), 0x09(1)   ← 长度或类型

校验和假设检验
  ✓ ★ 全部帧一致: 末字节 = 前面所有字节异或   ← 校验算法

常见协议头前缀检验
  疑似 AA AA 帧头: 42 帧命中   ← 确认 magic
```

## 二、408 字节车况偏移

**对应文件**：`NetaL/Models/VehicleState.swift` → `SignalLayout`

所有偏移当前都是 0，**抓包后必须校准**。

### 定位方法

**第 1 步：录多组不同状态的报文**

建议按这个顺序操作，每步单独录一帧：

1. 全关状态（静止）
2. 开后备箱
3. 关后备箱
4. 空调开 / 空调关
5. 制冷 / 制热
6. 车窗全开 / 全关
7. 开始充电 / 停止充电
8. 主驾座椅加热 1/2/3 档

**第 2 步：逐字节 diff**

对每一组，把 408 字节 dump 出来对比：

```
组A(关): AA BB CC 01 00 00 00 12 34 ...
组B(开): AA BB CC 01 00 01 00 12 34 ...
                    ↑        ↑
                  第3字节   第6字节变化 → 尾门状态 = 偏移6
```

只有 1–2 位变化的位置，就是该信号。

**第 3 步：判断宽度和类型**

| 变化情况 | 大概率类型 |
|---|---|
| 1 字节在 2–3 个值间跳变 | 状态枚举（门/锁/窗/挡位） |
| 1 字节 0/1 跳变 | 布尔（有效性标志） |
| 2 字节小范围变化 | 档位（风量、座椅档） |
| 2 字节数值随温度变 | 温度（除以 10，带符号） |
| 2 字节 0–10000 变 | 电量（除以 100） |
| 2 字节大范围递增 | 里程（可能 2 字节不够，需确认是否溢出处理） |

**第 4 步：填表**

```swift
var SignalLayout {
    var trunkState: Int = 6      // ← 填实测偏移
    var batterySoc: Int = 18     // ← 填实测偏移
    var socScale: Double = 100
    ...
}
```

填完后 `layout.isCalibrated` 会返回 true。

## 三、签名算法

**对应文件**：`NetaL/Core/NetaAPIConfig.swift` → `RequestSigner.sign`

```swift
enum Algorithm {
    case hmacSHA256      // 方案 A：HMAC-SHA256(appSecret, base)
    case sha256Concat    // 方案 B：SHA256(appSecret + base)
}
```

**怎么定**：

1. 用 Charles 抓原 APK 的任意请求，拿到 `signature` 参数值
2. 抓包拿到 `nonce` 值
3. 用已知 appSecret 分别算两种方案，比对哪个对得上

```bash
# 方案 A
echo -n "cappid:HOZON-B-xKrgEvMtappkey:e0ae...nonce:$NONCE" | \
  openssl dgst -sha256 -hmac "$APP_SECRET" -hex

# 方案 B
echo -n "${APP_SECRET}cappid:HOZON-B-xKrgEvMtappkey:e0ae...nonce:$NONCE" | \
  openssl dgst -sha256 -hex
```

比对抓包里的 signature 值。

**还要确认**：
- 输出大小写（十六进制是大写还是小写）
- 是否有额外字段参与（如 timestamp、deviceId）
- `channel` 在 iOS 端该传什么（当前写死 "ios"，原 APK 是 "android"）

## 五、指令载荷布局

**对应文件**：`TboeFrameCodec.encodeCommand()`

当前假设：

```
[type(1) | tag(1) | "090101" ASCII(6)]
```

**怎么定**：录开后备箱和关后备箱两帧，异或对比。

- 如果只有最后一个 ASCII 字符不同 → 布局正确
- 如果 tag 字节不同 → tag 位置不对
- 如果整个载荷结构不同 → 需要重新分析

同样要确认指令编码是 ASCII 字符串还是二进制字节。

## 六、挑战码签名

**对应文件**：`TboeTransport.handleChallenge()`

当前只有 TODO，没实现。

**需要确定**：

1. 挑战码载荷的字节序
2. 签名算法（推断 `SHA256withECDSA`，P-256）
3. **签名的字节序** —— 这是关键坑：
   - Security.framework 的 `SecKeyCreateSignature` 输出 DER 编码
   - 车端可能期望裸 `R || S` 拼接（64 字节）
   - 需要在两者之间转换
4. 签名是对原始挑战码，还是对它的哈希
