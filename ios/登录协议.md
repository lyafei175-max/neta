# 哪吒L 登录协议（APK 字节码逆向成果）

> 全部内容提取自 `哪吒L.apk.1` 的 `classes.dex`，方法级字节码证据，
> 混淆类名以 `L...;` 表示。标注：`[已确认]` = 字节码直接可见；`[推断]` = 合理猜测。

## 2. 签名算法 `[已确认]`

来源方法：`Ly1/u;->a(String path, List params, String json, String nonce, J timestamp)`

```
原串 = "POST"
     + <端点路径>
     + "appid:" + appId + "appkey:" + appKey + "nonce:"      ← 常量前缀（注意 appid 不是 cappid）
     + <nonce>
     + "timestamp:" + <毫秒时间戳>
     + ── 二选一 ──
       json 请求:  "json:" + <JSON body 字符串>
       表单请求:   每个 (k,v): k.toLowerCase(Locale.ROOT) + ':' + v   （直接拼接，无分隔符）
     + <appSecret>
```

```
sign = SHA256( JavaURLEncode(原串) )  → 十六进制字符串
```

关键点：
1. **先 URL 编码整个原串，再哈希**（顺序反了必错）。
2. Java `URLEncoder` 规则：空格→`+`；保留 `A-Za-z0-9 . - * _`；
   其余全部 `%XX`（大写 hex，含 `~`）。
3. 摘要输出 `[推断]` 小写 hex（Kotlin 惯例）；若服务端拒绝签名，
   依次尝试大写 hex → Base64。

## 3. 发送验证码 `[已确认]`

来源方法：`LA1/s0;->a()`

```
POST /pivot/account/2.0/sendCodeAndSignCheck
Content-Type: application/x-www-form-urlencoded;charset=utf-8

phone=<手机号>
```

- body 只有 `phone` 一个字段（以 `Pair("phone", value)` 列表传给构造器）。
- 签名走表单分支：原串中追加 `phone:<手机号>`。

## 4. 登录 `[已确认]`

来源方法：`LA1/e0;->a()`

```
POST /pivot/account/2.0/accountSafe/registerOrLoginUncheck
Content-Type: application/json

{
  "phone":      <手机号>,
  "code":       <短信验证码>,
  "appVersion": "6.4.2",
  "seriesNo":   <设备序列号, 由 Ls1/a;->a() 生成>,
  "deviceType": "2",
  "pushToken":  "app.netal"
}
```

- 签名走 JSON 分支：原串中追加 `json:` + 上面 JSON 的字符串形式。
- `seriesNo` 是设备维度的随机串，安装后保持稳定即可 `[推断]`。
- `deviceType: "2"` 疑似 android=2；服务端可能不校验 `[推断]`。

## 6. 响应结构 `[已确认 + 实测]`

来源方法：`Ly1/j;->h` 解析 + 服务器实打验证

```json
{
  "code": 0,
  "description": "验签信息缺失。",
  "data": {
    "token":    { "access_token": "...", "refresh_token": "...", "expires_in": 7200 },
    "customer": { "id": "...", "phone": "...", "nickName": "...", "name": "...", "profilePhoto": "..." },
    "vin": "..."
  }
}
```

- **token 在 `data.token` 下，不是 `data` 根层**（安卓用 `getString`，缺字段直接抛异常）。
  这是之前「登录失败」的直接原因。
- 服务端用的是 `description` 字段而非 `message`（实测返回 `{"code":40553,"description":"短信验证码错误"}`）。
- 成功码集合来自 `Ly1/m;-><clinit>`：`{0, 200, 1001, 20000, 42528}` `[已确认]`。

### 实测错误码语义

| code | description | 含义 |
|---|---|---|
| `30253` | 验签信息缺失。 | 验签 header 缺失或**名字大小写不对** |
| `40553` | 短信验证码错误 | 签名已通过，业务正常拒绝 |

## 6.1 Header 大小写敏感 `[实测]`

实测结论：网关对验签 header 名**大小写敏感**

| Header 形式 | 结果 |
|---|---|
| `appId` / `appKey` / `sign`（与 APK 一致，驼峰） | ✅ 进入业务逻辑（返回 40553） |
| 全小写 `appid` / `appkey` / `sign` | ✅ 同样通过 |
| 全大写 `APPID` / `APPKEY` / `SIGN` | ❌ 30253 验签信息缺失 |
| `Appid`（首字母大写，Python http 库默认） | ❌ 30253 |

因此客户端同时发送驼峰与全小写两套 header 名，避免 URLSession 归一化导致失配。

## 6.2 签名有效性验证 `[实测]`

用假手机号 + 假验证码直接请求生产接口：

```
POST /pivot/account/2.0/accountSafe/registerOrLoginUncheck
→ {"code":40553,"description":"短信验证码错误"}
```

返回「短信验证码错误」而非「验签失败」，证明签名原串、URL 编码、SHA-256 hex、
header 布局、appSecret 全部正确。**协议已跑通。**

## 7. 与旧实现的差异（本次修复点）

| 项 | 旧（错） | 新（对） |
|---|---|---|
| 签名原串前缀 | `cappid:` | `appid:` |
| 签名要素 | 只有 appId/appKey/nonce | + 端点路径 + timestamp + body + appSecret |
| 签名计算 | HMAC-SHA256 猜测 | SHA256(URLEncode(原串)) |
| 公共字段位置 | 放 body/query | 放 HTTP Header（大小写需精确） |
| sendCode 字段名 | `mobile` | `phone` |
| login body | `mobile`/`verifyCode` 表单 | `phone`/`code`/`appVersion`/`seriesNo`/`deviceType`/`pushToken` JSON |
| 响应字段 | `status`/`msg` | `code`/`description`/`data` |
| token 路径 | `data.access_token` | **`data.token.access_token`** |
